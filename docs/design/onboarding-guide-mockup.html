Proposal · product guide & first-run onboarding

Teaching Mokara without adding noise

Three formats, mocked against the real UI vocabulary (labels, chips and copy quoted from tasks/page.tsx, AppShell.tsx, teams/[id]/page.tsx, settings-view.tsx, analytics/page.tsx). Nothing here is built — this is the choice sheet. Section 05 lists the controls a guide must not document because they currently do nothing.

Recommendation: ship B first, then A. Hold C. A public /guide (marketing group, renders from HTML like /pricing) is the only option that costs no schema, no first-run flag and no new state — it is content, it is shareable, it answers "what is this?" before signup, and every in-app empty state can link into it the day it exists. A (the first-run card) is the higher-conversion half but needs a dismissal decision that touches the database, so it should land second and small. C (spotlight tour) is the most work for the least content: it needs the same flag, a measured-rect overlay, and it cannot point at a task drawer because there is no ?task= deep link yet. Park it behind A.

Getting started in Mokara

Five small things. Together they cover the whole product — a task with a deadline, broken into steps, shared with someone, weighed against a goal.

  1. Create your first task The + on the Todo header. A title is enough.
  2. Give it a due date Due date chip in the drawer, then Today or +7 days.
  3. 3 Break one into steps Steps when you create it — it becomes the Checklist. Open the new-task form →
  4. 4 Create a project or a KPI On the team page. Then weigh tasks toward it from the … panel. Go to Team →
  5. 5 Invite someone by @username The moment they accept, this workspace becomes a team. Go to Team →

How the ticks work (the real design question). Every item is derived from data the app already has — never a manual checkbox, because a checklist the user ticks themselves teaches nothing and lies the moment they click Dismiss. Items 1–2 and 4 come from the current container's task list and useContainerMeta (projects/KPIs already fetched); item 5 from member_count on the containers list. Two gaps to decide: (a) “your first task” is cross-container, but the board only knows the selected one — either accept per-container truth or add a small GET /me/onboarding summary; (b) “read the analytics page” can never be detected, so it stays a plain link and is not one of the five.
Dismissal is a database decision, not a component one. The house rule is server state over device storage (that is why last_container_id is a column and the cookie policy can promise “one session cookie”), so localStorage is out. Options: (i) derived-only — the card disappears when all five complete, with no way to dismiss early; (ii) one nullable users.onboarding_dismissed_at + a migration; (iii) derive “already knows the product” from existing data (any task older than the account's first day → never show) and ship with no schema change at all. (iii) is the cheapest honest version and is what the mockup assumes; (ii) is the one to pick if you want an explicit Dismiss that survives every device.

Chapter 03 · the task drawer

Inside a task

Click any row and the board gives up forty percent of its width. Everything you need to change about a task is in that panel — and almost all of it is one click or one keystroke away, with no save button anywhere.

Open it, then read it top to bottom

  1. Click a row on the board. The drawer's top bar shows the word Task and its short id (3F9A1C) — the same id the row carries.
  2. The title is read-only until you double-click it. Enter saves, Esc cancels.
  3. Under it, Created by jonas — immutable, and the reason assignment and authorship never get confused.
  4. Click the description to edit it. ⌘+Enter saves; Esc reverts; clearing the text removes it.

Change its state from the chip row

One line of chips, each opening a small menu: Todo / In Progress / Done / Canceled, then Low · Medium · High, then the due date, then the assignee. The … at the end folds three more: Project, KPIs and Flag.

Todo High Mar 5 J Jonas …
The drawer's chip row — identical in shape to the new-task form's.

Checklist, files, comments

  1. Checklist — the steps you wrote at creation. Tick them, double-click to rename, reorder with the arrows, delete on hover. The count beside the heading reads 2/5.
  2. Files — thumbnails for images, a download pill for PDFs. Only the person who uploaded a file can delete it.
  3. Comments — type and press ⌘+Enter. A plain Enter is a newline. Replies go one level deep; edit and delete are yours alone.
Two honest limits. Steps and task files are set when you create the task — the drawer has no “add a step” field and no upload button, so later material goes into a comment (which does take files). And Delete in the drawer's footer removes the task immediately, with no confirmation.
Close it with Esc — unless you are typing, in which case Esc cancels what you are editing first. There is no backdrop; the board stays visible and clickable beside the panel.

Placement: (marketing) or (app)? Both are one-line decisions, and they are not equivalent. (marketing) = app/(marketing)/guide/, public, AmbientCanvas + SiteHeader + SiteFooter, dynamic off the session cookie exactly like /pricing — a signed-in visitor gets a sidebar-less page and a “Open app” header CTA. (app) = inside AppShell, so it keeps the sidebar, the container switcher and the bell, but only signed-in users can read it and it costs an auth'd page load to answer a pre-signup question. The mockup above draws the (app) version because that is where the sidebar leaf lives; the recommendation is still (marketing) plus a deep link, since a guide that Google cannot reach does not help anyone deciding whether to sign up. Content lives in a data module (lib/guide.ts, the way lib/legal.ts and lib/pricing.ts already do) so the chapter rail cannot drift from the articles.

Why it is parked. It needs the same dismissal flag as Option A, plus a portal overlay that measures the target's rect and re-measures on scroll and resize — the exact idiom the Dropdown already uses, so the technique is not new, but it is five measured targets and a stack of edge cases (mobile drawer open, sidebar collapsed, the board scrolled). It also cannot teach the drawer, which is where most of the product lives, because there is no ?task=<id> deep link — a tour step cannot open a task on the user's behalf. If you want C, add the deep link first; it is independently useful (notification rows and due-soon rows currently can only switch container and push /tasks, which is the known UX-parity gap).

Voice rules for the copy

So it reads like the product, not like a manual.

  • Name the control by its on-screen label, in the same casing — “the + on the Todo header”, not “the add button”.
  • Say what happens, not what to feel. No “powerful”, no “seamless”.
  • State limits in the same sentence as the feature. The product already does this (Team projects & KPIs unlock when this workspace becomes a team).
  • Never document a control that does nothing — see section 05.
  • No emoji anywhere (house rule); keyboard glyphs ⌘ and Esc are text and stay.
  • Numbers come from one source. Caps are already rendered from lib/plans.ts via the API — the guide must not hand-type “3 members”.

Cheap wins that need no guide at all

Do these regardless of which option you pick.

  • The board empty state (No tasks yet · Capture a thought, get it done.) gains one line naming the + and the Steps field.
  • The None yet. project/KPI empty states already say where to go — make them links.
  • The drawer footer's Press Esc to close is the natural home for a “Guide” link.
  • The delete-in-drawer affordance has no confirmation: either add one, or the guide must warn (chapter 03 does).
  • Tooltip text for the row's priority bars already exists (Priority: high — click to cycle) — that is the pattern to extend, not reinvent.

06

Phasing and the questions only you can answer

Phase 1 — content, no state

One route, one data module, one sidebar leaf.

  • lib/guide.ts — chapters as data (title, minutes, sections, steps), the lib/legal.ts pattern.
  • /guide + /guide/[chapter] in the (marketing) group; shared chrome component so the rail cannot drift.
  • Sidebar leaf Guide (or a footer link beside Log out) — decide which, since (marketing) pages have no sidebar.
  • Empty states and the drawer footer link into the right chapter.
  • No migration, no atoms, no effects beyond the sticky-rail scroll spy.

Phase 2 — the first-run card

Only after the dismissal question is settled.

  • Decide (i) derived-only, (ii) users.onboarding_dismissed_at, or (iii) inferred-from-account-age.
  • If (ii): one migration + one nullable column, mirroring last_container_id.
  • Five items, all derived; each links to the chapter that explains it.
  • Entrance uses the existing stagger constants in lib/motion.ts — no new easings.

Blocked / decide first

Things that make a guide lie if written today.

  • Dead controls in section 05 — wire, hide, or omit.
  • Hardcoded seat numbers on the team page.
  • No task deep link → no tour of the drawer, and notification rows still cannot open the task they are about.

Questions for you

  • Who is the guide for — a signed-up user learning the board, or a visitor deciding whether to sign up? (Drives (marketing) vs (app).)
  • Public or private? Indexable help pages are free SEO and free support deflection; private keeps the product's internals out of search.
  • Screenshots? Every shot is a maintenance liability that goes stale on the next redesign. Recommendation: no bitmaps — render real component markup as illustration, the way this mockup does.
  • Video? Out of scope here; nothing in the stack serves it and it doubles the copy workload.
  • One page or ten? Ten chapters is a rail + routing; a single long page is one file and a sticky TOC (the legal docs already do this). The mockup draws ten; a single page is a legitimate cheaper answer.
  • Language — English only for now, or written to be translatable later (all strings in the data module either way)?
